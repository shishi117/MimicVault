# MimicVault の取得可能範囲と VideoDownloadHelper との比較

## 1. 取得・検出できる範囲(拡張機能側)

MimicVault は `webRequest`(ブラウザが発行する HTTP 通信を監視する API)でレスポンスを
覗き見る方式。**対象は HTTP(S) で流れるメディアのみ**で、WebRTC / RTMP / RTSP は仕組みの
外側のため検出不可能(`README.md`)。

| 規格 | 検出方法 | 取得(DL) | 制約 |
|---|---|---|---|
| 通常ファイル(mp4/webm/mkv 等) | DOM走査(`content/mediaDetect.js`)+`webRequest` | ブラウザ直DL | 拡張子固定リスト `MEDIA_EXTENSIONS` |
| HLS(.m3u8) | webRequest | companion経由MP4、未接続時は.ts結合 | 下記「暗号化・DRM」参照 |
| DASH(.mpd) | webRequest | トラック選択 + companion で mux | — |
| MSS(.ism/Manifest) | webRequest | DASH の URL 記法に書き換えて委譲(`background/ismToDashUrl.js`) | **動的パッケージャーのみ**。既知3記法(Unified Streaming/Azure/Wowza)を順に試すヒューリスティック。未知パッケージャーは失敗表示。静的Smooth(断片のみ・再パッケージ非対応)は非対応(moovビルダーが別途必要でコスト高) |
| 収集ストリーム(マニフェスト非露出MSE) | ディレクトリ単位でfMP4断片を収集(`background/segmentGroups.js`) | 結合してcompanionでremux | **再生し切った範囲のみ取得可**(ライブ録画と同じ制約)。1ディレクトリに複数レンディション混在だと先頭initを使うため壊れる場合あり。TS断片・連番.mp4・init無しSmooth Fragmentsは対象外 |

`background/domainFilter.js` でホワイトリスト/ブラックリスト(ワイルドカード対応)による
ドメイン単位の除外も可能。

## 2. companion アプリで変換できる範囲

Native Messaging(ブラウザ拡張がローカルのネイティブアプリとやり取りする仕組み)経由で
FFmpeg を呼び出す別プロセス(`companion/app.js`)。対応コマンドは3つのみ
(`docs/コンパニオンアプリ.md`, `companion/lib/handleMessage.js`)。

- `convert`:HLS→MP4変換
- `mux`:DASHの映像+音声トラックを結合してMP4化
- `remux`:収集ストリームの結合済み断片→MP4

**companionが行わないこと**:インターネット以外へのデータ送信、変換完了ファイル以外の
データ保持。未接続時は検出はできても変換できず、生の.ts/断片化mp4のまま保存される。

## 3. 暗号化・DRMの制約

| 方式 | 対応状況 |
|---|---|
| AES-128(HLSの標準的な暗号化) | ✅対応。`background/hlsCrypto.js` で `SubtleCrypto`(ブラウザ標準の暗号API)により復号 |
| SAMPLE-AES | ❌非対応。`background/hlsMediaParse.js` で検出した時点でエラー、ポップアップにも「DRM保護コンテンツは未対応」と表示 |
| Widevine/PlayReady/FairPlay/EME(ライセンスサーバーと鍵交換する本格DRM) | ❌完全に非対応。コードベースに該当処理は一切なし。暗号化MSEを使うサイトは再生可能なURLとして観測できないため検出自体が不可 |

## 4. 既知の簡略化・アップグレードパス(次の実装候補)

コード内コメントで明示されている着手候補:

1. **静的Smooth Streaming対応**:CodecPrivateDataからfMP4 initを生成する「moovビルダー」が必要。コスト高。
2. **収集ストリームの複数レンディション分離**:v1は未対応。大半は実害なしだが混在レイアウトで壊れる。
3. **SAMPLE-AES/本格DRM**:ライセンス管理が必要な領域で、ブラウザ拡張単体では原理的に困難。
4. **WebRTC/RTMP/RTSP**:`webRequest`の検出モデルの前提から外れるため、対応するなら別アーキテクチャ(MediaRecorder APIでの録画等)が必要。

## 5. VideoDownloadHelper(VDH)との比較

VDH は非公開ソースの製品のため、以下は公開されている一般的な挙動・知識に基づく比較で
あり、MimicVault側のみコード確認済み。

### 5.1 対応形式/機能面

| 観点 | MimicVault | VDH |
|---|---|---|
| 通常ファイル/HLS/DASH | ✅両方対応 | ✅両方対応 |
| サイト別アダプタ(特定サイト専用の抽出ロジック) | **なし**。汎用的なURL/MIMEパターン検出のみ | **あり**。YouTube等主要サイト向けの専用抽出ロジック("variants")を長年蓄積 |
| マニフェスト非露出の独自プレイヤー(MSE) | ✅汎用フォールバックあり(収集ストリーム)。サイト名を知らなくても機械的に拾える | 専用variantが無いサイトは基本的に検出不可 |
| MSS(Smooth Streaming) | ✅明示対応 | 明示的な対応は一般に知られていない |
| DRM(Widevine等) | ❌非対応 | ❌非対応(両者共通の壁) |
| 出力フォーマットの種類 | `convert`/`mux`/`remux`の3種のみ。元画質のまま1本のMP4化に限定 | 変換はFFmpeg相当(libav)のWASM版を拡張内蔵で実行(後述5.3)。選択肢の広さは未検証 |
| ブックマーク連携一括DL | ✅独自機能 | 一般には知られていない(MimicVault独自の可能性) |
| ライブ配信録画 | ✅30セグメント単位のチャンク分割保存 | ✅同様の機能を持つ(詳細非公開) |

### 5.2 アーキテクチャ/実装方式

> **訂正(2026-10-06)**: 本節は当初、VDHの実ソースを確認せず一般知識/推測で記述していた。
> 実際にVDH本体(v10.5.49.2、Manifest V3版)の展開済みソースを調査した結果、
> 「companion appを使う」「サーバー駆動でルールを配信する」という記述は**誤り**と判明した。
> 詳細は5.3節を参照。以下は訂正後の内容。

| 観点 | MimicVault | VDH(v10.5.49.2で確認) |
|---|---|---|
| 基本方式 | WebExtension(`webRequest`監視+DOM走査) | 同じくWebExtension方式(Manifest V3) |
| 変換処理 | companionアプリ必須(Native Messaging経由でffmpeg実行) | **外部コンパニオンアプリ不要**。FFmpeg相当(libav)をWASM化して拡張内に同梱し、MV3の`offscreen`API(非表示ページでの重い処理を許すAPI)上で実行 |
| サイト別ルールの更新方式 | 完全ローカル・静的。companionはネットワーク外通信なし | **静的・バンドル方式**。`manifest.json`の`content_scripts`にサイトのURLパターンを直接列挙しており、対応サイトの追加は拡張本体の更新(Chrome Web Store経由)でのみ起こる。実行時にサーバーからルールを取得する仕組みは見つからなかった |
| 対応ブラウザ | Firefox限定(ESR/Developer Editionのみ、未署名のためRelease不可) | Chrome/Edge等(確認したビルドはManifest V3のChrome系) |
| 配布・インストール形態 | 未署名XPIをenterprise policyで強制インストール(個人/組織内利用前提) | 公式署名拡張としてChrome Web Store等から一般配布(`update_url`がGoogle公式のものを指す) |
| コードの透明性 | companion含め全てOSSとして閲覧・ビルド可能 | クローズドソース。ビルド済み(minify済み)JSとして配布されており、今回は展開して静的解析した |
| nativeMessaging/companion関連の記述 | `nativeMessaging`権限あり、`companion/`ディレクトリに実装あり | `manifest.json`に`nativeMessaging`権限なし。コード内に`coapp`/`companion`/`nativeMessaging`の文字列は検出されず |

**まとめ(訂正後)**: 技術的な骨格(`webRequest`監視+DOM/ページJS解析)という大枠は似ているが、
変換処理を外部ネイティブアプリに依存するか、拡張内蔵のWASMで完結させるかという点でMimicVault
とVDHは明確に異なるアーキテクチャを採っている。またサイト別対応はVDHも**動的配信ではなく
静的バンドル**であり、両者とも「ルールはビルド時に決まる」という点では共通している。

### 5.3 サイト別ルール("variant")の実装構造(VDH実ソース調査、2026-10-06)

ユーザー提供のVDH展開済みソース(v10.5.49.2、Manifest V3)を静的解析した結果。

**ファイル構成**:

```
manifest.json          ← content_scripts にサイトのURLパターンを静的列挙
injected/
  <site>.js             (ISOLATED world)  ← 拡張コンテキストで動く司令塔役
  <site>_untrusted.js   (MAIN world)      ← ページ自身のJSコンテキストに直接挿入
service/main.js        ← background service worker
download_worker/, service/*.wasm ← libav(FFmpeg相当)をWASM化したもの
```

対応サイト数は約15(YouTube, Vimeo, Facebook/Instagram, ok.ru, VK, Canva, iq.com,
TwitCasting, Bilibili, taiav.com, osmosis.org, Kick, Chaturbate, 91porna.com,
javrank.com)。いずれも**人間が個別に書いたJavaScript**であり、汎用ルールエンジンや
DSL(ドメイン特化言語)は見当たらなかった。

**要素**:

1. **ISOLATED world script**(`<site>.js`):`chrome.*` APIにアクセス可能。background
   serviceとやり取りする司令塔役。
2. **MAIN world script**(`<site>_untrusted.js`):ページの実行コンテキストに直接挿入され、
   そのサイト固有のJSグローバル変数を読める(例:Vimeoの`window.playerConfig`、Bilibili
   の`window.__initialState`、iq.comの`window.__playerdata__`、YouTubeの`window.ytcfg`)。
   "untrusted"と呼ぶのは、ページ自身に汚染されうるコンテキストで動くため役割を「値を読んで
   中継するだけ」に絞って信頼境界を小さくしているから。
3. **通信路**:`BroadcastChannel`(同一タブ内の複数コンテキストが通信できるブラウザ標準API)
   を使った内製の軽量メッセージバス。チャンネル名は`injected-${hash(location.href)}`で
   ページ単位に分離し、メッセージには`FromUntrustedInjectedToTrusted`等の列挙値でタグ付け。
   命名規則は`<site>_on_<何か>`(結果通知)/`<site>_request_<何か>`(再取得依頼)で統一。

**抽出方法の実例**(サイトごとに手段が異なる):
- Vimeo:`window.playerConfig`が出現するまで指数バックオフでポーリング
- Bilibili:`window.__initialState`/`window.__INITIAL_STATE__`を読む
- javrank.com:`XMLHttpRequest.prototype.open`をモンキーパッチして`.m3u8`レスポンスを横取り
- twitcasting.tv:サイトの非公開API(`streamserver.php?target=...`)を直接fetchしてHLS URL
  を取得し、そのURLを自分で`fetch()`することで拡張の通常検出パイプラインに流し込む。SPA遷移は
  `MutationObserver`で検知して再実行
- 91porna.com(`xgplayer_crypto`):サイト独自の暗号化HLSに対する専用復号ロジックを持つ

**作成方法(推測を含む)**:
- サイトの追加・変更は拡張本体のビルド・ストア更新でのみ反映される(5.2節参照)。
- 各ファイルはビルドで圧縮(minify)されており、Promiseポリフィル等の共通ランタイムが
  各ファイルの先頭に重複して埋め込まれている(≒バンドラで個別ファイルとして出力)。
- 汎用データ駆動ルールではなく、**サイトごとに人間が書いたスクレイピング/モンキーパッチ
  コードの集積**、というのが実態。

**MimicVaultとの対比**: MimicVaultは汎用検出(URL/MIME/DOM走査)のみでサイト別コードを
持たない。VDHは汎用検出に加えて主要サイトごとの専用コードを持つ、という構成の違いがある。
サイト別対応を追加する場合、VDHの模倣ではなく「対象サイトを絞り、
`{matchPattern, extractor, nameTemplate}`のような最小構造から要件ベースで設計する」方が
現実的と考えられる。
